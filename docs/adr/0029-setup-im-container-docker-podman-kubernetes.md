# ADR 0029: Setup standardmäßig im Container – Docker, Podman oder Kubernetes, Image lokal gebaut

- Status: angenommen
- Datum: 2026-09-30
- Bezug: Anforderung des Product Owners 2026-09-30, Team-Entscheidung T15, ADR 0008 (nicht vertrauenswürdiger Code nur im Container), ADR 0028 (Nachtrag: keine npm-Veröffentlichung)

## Kontext

OpenVideo wird nicht auf npm veröffentlicht; jeder baut es aus dem Repository. `SETUP.md` ist eine Anleitung, die ein
Coding Assistant liest und ausführt, und `npm run setup` baute bisher nativ auf dem Host: `npm ci`, Build, Chromium
über Playwright, `npm install -g ./packages/cli`. Das verlangt die passende Node-Version, FFmpeg und die
Systembibliotheken von Chromium auf dem Host und verändert den globalen npm-Ordner.

Der Product Owner verlangt: „Das Setup soll als default in docker / podman / kubernetes erfolgen, was im Zugriff ist und
vom / oder vom Kunden angegeben! Das Image soll lokal per jeweiliger tech gebaut werden.“

## Entscheidung

### 1. Laufzeit-Wahl

`npm run setup -- --runtime <auto|docker|podman|kubernetes|native>`, alternativ `OPENVIDEO_RUNTIME`. Vorrang:
Option > Umgebungsvariable > gespeicherte Wahl der letzten Einrichtung > `auto`. `auto` prüft in dieser Reihenfolge, was
wirklich nutzbar ist:

1. **Docker:** Programm vorhanden und `docker info` antwortet (Daemon erreichbar). Ein `docker`, das in Wahrheit Podman
   ist (`podman-docker`), zählt als Podman.
2. **Podman:** `podman info` funktioniert (unter macOS/Windows läuft die Podman-Maschine); rootless wird erkannt.
3. **Kubernetes:** `kubectl` vorhanden, Kontext gesetzt, `kubectl version --request-timeout=5s` antwortet, und ein
   Image-Builder ist nutzbar (docker, podman, nerdctl, buildah – in dieser Reihenfolge, oder `--builder`).
4. **Native** nur als letzter Rückfall mit deutlicher Meldung, oder wenn ausdrücklich gewählt.

Eine ausdrücklich gewählte, aber nicht nutzbare Laufzeit ist ein Fehler (Exit-Code 1) mit der Erkennung aller
Kandidaten; das Setup weicht dann nicht still auf eine andere aus. Gewählte Laufzeit, Grund und Einstellungen stehen in
der Ausgabe und in `runtime.json` im Konfigurationsverzeichnis (`OPENVIDEO_CONFIG_DIR`, sonst
`$XDG_CONFIG_HOME/openvideo`, `~/.config/openvideo`, unter Windows `%APPDATA%\openvideo`), Rechte 0600. `--dry-run`
zeigt Erkennung, Builder, Befehle und Wrapper-Inhalt als JSON und ändert nichts.

### 2. Image lokal mit der jeweiligen Technik

Ein Dockerfile (`deploy/docker/Dockerfile`), neues Ziel **`local`**: `render-cpu` (Node 22, Anwendung, Schriften,
FFmpeg 7.1, Chromium) plus Studio; mit `--with-blender` auf Basis des Ziels `blender` (`ARG LOCAL_BASE`). Tags
`openvideo-local:<version>` und `openvideo-local:latest`. Kein Pull fertiger Images aus GHCR.

- Docker: `docker build` mit BuildKit. Podman und Buildah: `build --format docker` (sonst ignoriert das OCI-Format die
  `SHELL`-Anweisung) und `--ignorefile deploy/docker/Dockerfile.dockerignore`. nerdctl: `build` (unter Rancher Desktop im
  Namespace `k8s.io`).
- Podman-Kompatibilität: Basis-Image voll qualifiziert (`docker.io/library/node…`, keine Kurznamen-Auflösung).
  `ADD --checksum` kennt Buildah vor 1.37 nicht (Ubuntu 24.04: Podman 4.9, Buildah 1.33); die Archive von Chromium und
  Blender lädt deshalb `deploy/docker/fetch.mjs` im Build und prüft ihre SHA-256, danach zusätzlich `sha256sum -c`.
- Hinter einem TLS-Proxy: `--ca-cert <datei>` (Standard: `NODE_EXTRA_CA_CERTS` des Hosts) geht als Build-Secret `ca`
  an `npm ci` und die Downloads; es landet nicht im Image.
- Chromium und Blender gibt es nur für amd64: `--platform linux/amd64` (Apple Silicon emuliert).
- Aktualisieren: `git pull && npm run setup` nimmt die gespeicherte Laufzeit und baut neu; der Layer-Cache greift.

### 3. Befehl `openvideo` auf dem Host: Wrapper

Das Setup installiert ein erzeugtes POSIX-Shellskript `openvideo` in ein Bin-Verzeichnis (Standard `~/.local/bin`,
`--bin-dir`; Hinweis, wenn es nicht im `PATH` liegt, und Warnung, wenn ein anderes `openvideo` vorher kommt). Unter
Windows (Docker/Podman) `openvideo.ps1` und `openvideo.cmd`. Das Setup überschreibt nur Dateien mit der Markierung
`openvideo-wrapper: generated by npm run setup` und entfernt den Wrapper beim Wechsel auf native.

**Docker/Podman:** `run --rm -i` (plus `-t` bei Terminal, nie für `mcp`), `--pull never` (nur das lokal gebaute Image,
kein gleichnamiges aus einer Registry), `--security-opt no-new-privileges`, `--cap-drop ALL`, `--shm-size 512m`, kein
`--privileged`. Nutzer-ID des Aufrufers (`--user $(id -u):$(id -g)`, Podman rootless zusätzlich `--userns=keep-id`):
erzeugte Dateien gehören dem Nutzer. Cache im benannten Volume `openvideo-cache-<uid>` unter `/var/cache/openvideo`
(im Image mit Sticky-Bit für alle beschreibbar; je Nutzer ein Volume, damit sich Nutzer eines Hosts keine
Cache-Einträge unterschieben). `OPENVIDEO_*` des Hosts gehen mit Namen durch (die Werte liest die Engine aus der
Umgebung), außer Host-Pfaden (`OPENVIDEO_FFMPEG`, `OPENVIDEO_CHROMIUM`, `OPENVIDEO_CACHE_DIR` …). Argumente gehen
unverändert als `"$@"` durch – nie über `eval` oder eine zweite Shell-Auswertung.

Abweichung vom ursprünglichen Vorschlag `/work`: Der aktuelle Ordner wird **unter demselben absoluten Pfad** eingehängt
und ist das Arbeitsverzeichnis; ebenso `--workspace`, `--project` und `OPENVIDEO_WORKSPACE`, wenn sie außerhalb liegen
(`--workspace` wird vorher als Nutzer angelegt). Grund: Pfade in Ausgaben, Render-Manifesten und MCP-Antworten stimmen
dann auf dem Host, und `claude mcp add openvideo -- openvideo mcp --workspace ~/openvideo-projects` funktioniert
unverändert. Unter Windows gibt es keinen gleichen Pfad; dort `/work`, `/mnt/workspace`, `/mnt/project`. Pfade mit
`:` lehnt der Wrapper mit einer Meldung ab. Auf SELinux-Hosts (erzwingend) setzt er `--security-opt label=disable`, statt
den Nutzerordner mit `:z` umzuetikettieren.

`--init` entfällt: Das Image startet `tini` als PID 1; ein zweiter Init-Prozess würde warnen, und Podman bräuchte dafür
`catatonit`.

`serve`, `dev`, `studio`: Port nur auf Host-Loopback (`-p 127.0.0.1:<port>:<port>`), im Container `--host 0.0.0.0`
(sofern nicht angegeben) und `--no-open`. Auf `0.0.0.0` braucht die API ein Token: Das Setup erzeugt es zufällig
(32 Bytes) in `api.env` (0600) und behält es bei Updates; der Wrapper übergibt es mit `--env-file`, nie auf der
Kommandozeile. `OPENVIDEO_PUBLIC_URL=http://127.0.0.1:<port>` lässt die CLI die Links mit der erreichbaren Adresse
ausgeben; bei `dev`/`studio` trägt die Studio-URL das Token im Fragment (`#token=`), bei `serve` gibt der Wrapper die
URL mit Token auf stderr aus.

`dev` im Container: Unter Linux melden Bind-Mounts Änderungen per inotify. Für Docker Desktop/Podman-Maschinen unter
macOS/Windows gibt es `OPENVIDEO_WATCH_POLL_MS`: Datei-Watcher (`watch.ts`) und Revisionsbeobachtung des Servers
(`RevisionWatcher`) fragen dann zusätzlich ab. Der Wrapper setzt 1000 ms unter macOS und Windows.

`mcp` läuft über stdio (`-i` ohne `-t`); Ende von stdin beendet den Server mit Exit-Code 0.

`doctor` meldet die Laufzeit (`OPENVIDEO_RUNTIME_INFO`, vom Wrapper gesetzt) und erklärt im Container, dass es dort
kein Docker gibt: eigene TSX-Projekte laufen mit `--trusted` im Container, der nur die eingehängten Ordner sieht;
fremde TSX bleiben einer nativen Einrichtung mit Docker-Sandbox vorbehalten (ADR 0008). Das Image setzt
`OPENVIDEO_WORKSPACE` leer; leer gilt jetzt als nicht gesetzt, damit wie nativ `.openvideo-workspace` im aktuellen
Ordner bzw. der Ein-Projekt-Workspace bei `--project` gilt.

GPU: `--gpu` nur, wenn `nvidia-smi -L` und das NVIDIA Container Toolkit (Docker-Runtime `nvidia` oder CDI) da sind;
der Wrapper reicht dann `--gpus all` bzw. `--device nvidia.com/gpu=all` durch. Das Ziel `render-gpu` unterscheidet sich
von `render-cpu` nur durch Umgebungsvariablen; ein eigenes lokales GPU-Image ist deshalb nicht nötig.

### 4. Kubernetes

Das Setup deployt den **neuen schlanken Stack `deploy/k8s/overlays/dev`** statt `overlays/local`: ein Pod
`openvideo` (CLI, Agent API, Studio; Image `openvideo-local`), Workspace-PVC, Service, NetworkPolicy ohne ausgehenden
Verkehr. `overlays/local` bringt Koordinator, Worker, KEDA, SeaweedFS und feste Test-Tokens mit – für einen Entwickler zu
schwer, und KEDA müsste zuerst clusterweit installiert werden.

Das Image baut der erste nutzbare Builder lokal, mit eindeutigem Tag `<version>-<image-id>` (damit ein neuer Build den
Pod neu startet), und bringt es in den Cluster: kind (`kind load docker-image` bzw. `image-archive`), minikube
(`minikube image load`), k3d (`k3d image import`), k3s (`k3s ctr images import` bzw. `ctr -n k8s.io`, mit `sudo`,
wenn nicht root), Docker Desktop/Rancher Desktop (lokales Image direkt), sonst `--registry <host/path>` (tag, push).
Ohne passenden Weg bricht das Setup vor dem Build mit den Optionen ab. Das Setup erzeugt im Konfigurationsverzeichnis
ein Overlay (`kubernetes/kustomization.yaml`), das `overlays/dev` einbindet und Namespace (Pod Security `restricted`,
Standard `openvideo-local`, `--namespace`), Image (kustomize `images:`) und das Secret `openvideo-local` aus `api.env`
setzt – nichts davon im Repository. Danach `kubectl apply -k` und `rollout status`.

Der Wrapper führt Befehle per `kubectl exec` im Pod aus:

- `mcp` → `kubectl exec -i deploy/openvideo -- openvideo mcp --workspace /workspace` (Ordner des Hosts werden ignoriert,
  mit Hinweis).
- `serve`/`studio` → `kubectl port-forward --address 127.0.0.1 svc/openvideo 7788:7788`, Studio-URL mit Token aus `api.env`.
- `doctor`, `templates`, `--help` → direkt im Pod.
- Befehle mit Dateien (`create`, `validate`, `render`, `render-frame`, `op` …): Der aktuelle Ordner wird per `tar` über
  `kubectl exec` nach `/var/cache/openvideo/host/<cksum des Pfads>` gespiegelt (ohne `node_modules`, `.git`, `out`,
  `.openvideo`, `.openvideo-workspace`; nicht aus `$HOME` oder `/`), der Befehl läuft dort, und alle Dateien, die er
  neu schreibt oder ändert, kommen in denselben relativen Pfad zurück. Der Exit-Code bleibt erhalten. `op` ohne
  `--workspace`/`--project` arbeitet im Workspace des Pods (wie MCP und Studio).
- `dev`, `worker`, `coordinator` → nicht verfügbar (Exit-Code 2 mit Ausweg): `dev` beobachtet Dateien auf dem Rechner,
  Worker gehören zu `overlays/production`.

Pfade in der Ausgabe von Befehlen mit Dateien nennen den Ordner im Pod; die Dateien liegen danach am selben relativen
Ort auf dem Host.

### 5. Native

Wie bisher (`npm ci`, Build, Chromium, `npm install -g ./packages/cli`, `doctor`) mit den Schaltern `--skip-install`,
`--skip-build`, `--skip-browser`, `--with-deps`, `--no-link`.

### 6. Prüfung

`scripts/test/setup.test.mjs` und `setup-wrapper.test.mjs` prüfen Erkennung, jede Laufzeit, jeden Kubernetes-Pfad und
die Wrapper mit Stub-Programmen in einem eigenen `PATH` (Aufrufe werden protokolliert), einschließlich Argumenten mit
Leerzeichen und Shell-Zeichen, TTY, Ports, Token-Übergabe und der Dateispiegelung in einen simulierten Pod. Der
Workflow `setup-smoke.yml` baut das Image mit `--runtime docker` und fährt die Rauchprobe über den Wrapper
(create, validate, render-frame, MCP-Handshake).

## Folgen

- Auf dem Host braucht OpenVideo nur noch Node.js für das Setup-Skript und eine Container-Laufzeit; FFmpeg, Chromium und
  Schriften sind im Image, und alle Nutzer bekommen dieselben Versionen wie die offiziellen Images.
- Der erste Build dauert einige Minuten und belegt rund 2,5 GB; Updates bauen nur geänderte Schichten neu.
- Befehle starten einen Container (rund 1–2 s Mehraufwand je Aufruf); `serve`, `dev`, `studio` und `mcp` laufen
  dauerhaft und merken davon nichts.
- Im Container fehlt die Docker-Sandbox für fremde TSX-Projekte; eigene laufen mit `--trusted`. HTML-Skripte bleiben ohne
  Chromium-OS-Sandbox gesperrt wie in den offiziellen Images.
- Unter Kubernetes kopiert jeder Dateibefehl den Projektordner; große Ordner machen ihn langsam. `dev` gibt es dort nicht.
- Pfade mit `:` lassen sich nicht einhängen; der Wrapper meldet das.
